# workplan

## 這個 skill 在做什麼

使用者的工作真相分散在三個地方,這個 skill 負責把它們接起來,但每一層的角色是固定的,不要混用。

| 系統 | 角色 | 讀寫 |
|---|---|---|
| Notion 12 個「任務追蹤-*」database | 任務來源 | 全程唯讀,絕不回寫狀態 |
| 提醒事項 | 待辦主要載體,只有日期沒有時間 | 讀寫 |
| iCloud 行事曆「工作」系列 | 只放討論後確認的重點,才有具體時間 | 讀寫 |

四個不變量必須守住。第一,Notion 永遠唯讀,使用者的完成動作只發生在提醒事項。第二,平鋪出來的待辦只設日期,不要改成帶時間。第三,行事曆事件只在使用者明確挑選後才建立,不可以自動把整批待辦倒進行事曆。第四,**重排行程一定要等使用者點頭**,早上的推播只回報現況與待決定的事,不會自己把行程改掉。

## 預設走口述,不要動不動就讀 Notion

使用者講的工作粒度比 Notion 任務粗,而且他自己最清楚今天該做什麼。所以預設流程是**他口述、你用 `add` 建待辦並直接排時段**,一步到位。

Notion 那套(`plan` 從十二個 database 抓任務、依到期日與優先順序排序)只有在他明確說「去看一下 Notion 有什麼沒做完」時才用。不要每次排工作都先跑 `plan`,那要八秒而且排出來的顆粒度往往不是他要的。

你平常只需要認得專案名稱。同一個專案往往有好幾種口語說法,對應表在 `references/project_map.json` 的 `aliases`。認不出來時腳本會列出可用代號並要求你補別名,不要自己猜。

## 排序規則（只有走 `plan` 讀 Notion 時才適用）

任務排序只看任務本身的欄位,不做專案層級的主觀判斷,因為專案的緊急程度會動態變動。順序是到期日近的先,同組看「優先順序」欄位的高中低,再看「難度」欄位,大的先開始以免來不及。

每日容量上限寫在 `wp/config.py`,目前是一天最多三個不同專案、每個專案最多三件、一天總計最多八件。哪三個專案不由 skill 指定,而是照任務隊列自然浮現,一天湊滿三個專案就換下一天。

年度計畫頁(`ROADMAP_PAGE_ID`,選用)不參與計算,它純粹是背景知識,只在報告尾端顯示本月安排供參考。使用者不一定要照它調整,不要拿它去推翻使用者指定的專案範圍。

## 主要流程

腳本就在這個 skill 目錄下,用 `python3 workplan.py` 執行,沒有外部依賴。下面的指令都以 skill 目錄為工作目錄,實際執行時要換成完整路徑。

第一次使用如果報「還沒完成初始化」,那是 `bin/wpkit` 還沒編譯。叫使用者跑 repo 根目錄的 `setup.sh`,不要自己想辦法繞過,那支工具是所有讀寫的唯一入口。

### 排工作:一個指令

```bash
cat <<'JSON' | python3 workplan.py add --list 提醒事項
[
  {"project":"官網改版","title":"分析新需求","day":"2026-03-02","minutes":120},
  {"project":"內部工具","title":"修正登入 bug","day":"2026-03-03","minutes":180}
]
JSON
```

`add` 會建待辦、掛專案標籤,**然後直接把它們卡進行事曆空檔**,不用再跑第二個指令。只想建待辦不排時段就加 `--no-schedule`。

清單歸屬每次都問,不要記成固定規則,現有清單用 `workplan.py lists` 查。`minutes` 只影響行事曆事件長度,提醒事項一樣只有日期。

待辦標題只有任務名稱,專案靠**原生標籤**表示,備註保持空白。

**行事曆事件的備註也只放人看得懂的東西。** 多件合併時列出合併了哪幾件,單件就完全空白。不要寫 `提醒事項:<uuid>` 那種關聯記錄,一打開事件那串亂碼就糊在臉上。事件與待辦的對應存在 `cache/plan-latest.json` 的 `event_uids`,專案、順延次數、時段基準也都在那裡。

### 不是每件待辦都該進行事曆

行事曆保護的是**整段不被打斷的時間**,不是待辦清單的鏡像。半小時的雜事塞進去只會把版面切碎,真正的重點反而看不出來,而且那種事本來就只需要一個日期。

門檻寫在 `wp/config.py` 的 `MIN_EVENT_MINUTES`,目前是六十分鐘,不到的只留在提醒事項。門檻套在**合併後的整組**上,所以同一天同專案的兩件半小時小事湊成一小時仍然會排進去。被擋掉的項目腳本會列出來。

使用者用 `focus --pick` 明確指定編號時不套門檻,那是他自己決定要保護那段時間。

### 排時段的規則

`focus` 單獨跑時預設排「全部還沒有時段的待辦」,不用抄編號;只想排特定幾件才加 `--pick 4,13`。

排時段會自動處理這些:讀當天所有行事曆的忙碌時段並避開、套用 `BLOCKED_BLOCKS` 設定的封鎖時段、跳過 `OVERLAPPABLE_EVENT_TITLES` 列的可重疊行程、單一空檔塞不下就切成同一天的幾段、同一天同專案合併成一個時段、依專案落到對應顏色的行事曆。

**專案要分色,一本行事曆一個專案。** 顏色是行事曆屬性而不是事件屬性,全部塞在「工作」裡的話週檢視會整片同色,一週有兩三個專案就分不出誰是誰。對應表在 `wp/config.py` 的 `PROJECT_CALENDARS`,預設是空的,沒列到的專案一律落回 `TARGET_CALENDAR`。`focus` 會自動選對行事曆,不用手動搬。

建議一開始只替常跑的三到五個專案分色,其餘留在預設那本。分太細的話側邊欄會塞滿行事曆,反而難管理。配色照 `config.py` 的 `SUGGESTED_COLORS` 順序取用就不會撞色,前兩個是藍與橘,區辨最強而且對色盲友善。

新專案要分色時,先用 `wpkit mkcalendar` 建行事曆並指定顏色,再把專案補進 `PROJECT_CALENDARS`、顏色補進 `PROJECT_CALENDAR_COLORS`,**並且一定要把新行事曆加進 `BUSY_CALENDARS`**,漏掉的話排程會把已經排好的工作當成空檔重複排進去。選色以藍與橘這類強對比為優先,對色盲也分得出來。

```bash
echo '[{"title":"工作-官網改版","color":"#16A34A"}]' | bin/wpkit mkcalendar
cat <<'JSON' | bin/wpkit movecal   # 搬既有事件,uid 不變所以 cache 不會斷
[{"uid":"...","calendar":"工作-官網改版"}]
JSON
```

**固定不排工作的時段**寫在 `wp/config.py` 的 `BLOCKED_BLOCKS`,key 是星期幾(週一為 0)。例如把週三下午留給例行會議就寫 `{2: [("13:00", "18:00")]}`,預設不封鎖。

`OVERLAPPABLE_EVENT_TITLES` 列的既有事件不算佔用時段,工作可以蓋過去,適合那種掛著但不需要專心的行程。使用者說某個行程可以重疊時,把關鍵字補進這裡,不要每次手動閃避。

一件任務的時數塞不進任何單一空檔時,腳本會自動切成幾段分散在同一天,標題後面加上分段序號,總時數不變。每段不短於 `SPLIT_MIN_SEGMENT`(六十分鐘)。全天空檔加起來仍然不夠才會落成未排入,那時候要問使用者是延到別天還是壓縮既有行程。

同一天同一專案的任務會**合併成一個時段**,腳本先用頓號串接原始標題,備註列出合併了哪些。實際做的時候本來就是連著做,切成好幾個小事件只會讓行事曆變瑣碎。提醒事項那邊仍然是獨立的幾筆,可以一件一件勾。

**`focus` 跑完之後,每一個新建事件的標題都要重新產生成簡短版,這是必做步驟,不是只有合併的那幾件。** 腳本產生的標題是待辦名稱直接串接,那是給你看的中間產物,不是最終標題。你要逐一取一個概括該時段在做什麼的短標題,再用 `wpkit retitle` 一次改掉。行事曆格子塞不下一長串,使用者看到的只會是被截斷的一段字。明細已經在備註裡,標題不需要重複。

```bash
cat <<'JSON' | bin/wpkit retitle
[{"uid":"...","title":"[官網改版] 前台改版:驗證與稽核"}]
JSON
```

uid 用 `wpkit events <start> <end> <行事曆名稱>` 取得,拿 `start` 當索引對回你剛排的時段。概括的原則是抓那幾件事的共同主題,例如權限驗證加欄位檢查加稽核記錄就寫成「驗證與稽核」,不要寫成沒有資訊的「三件雜項」。分段事件保留 `(1／2)` 這種序號,使用者要看得出這件事跨了兩個時段。

`evening` 標完成勾號時會讀事件現有標題再加勾號,不會用待辦名稱重組,所以你改短的標題不會被洗掉。

兩種情況會拆開。使用者明確說要分開時加 `--split`,或者同一天同一專案超過三件時腳本自動拆,因為一個標題塞四五件事就看不出重點了。上限寫在 `wp/config.py` 的 `MERGE_MAX_TASKS`。

### 每天的節奏

```bash
python3 workplan.py today     # 今天要做什麼
python3 workplan.py status    # 計畫跟現實差在哪
```

launchd 每個平日跑兩次,早上 08:30 跑 `status --notify`,傍晚 18:00 跑 `evening --notify`,都會同時發 Telegram(走 `~/bin/tg-notify.sh`)與本機通知,不需要手動跑。

### 動態調整:先對現況,再問,才重排

使用者會在行事曆上直接拖動事件、提早做完就把隔天的拉過來做、或是整件沒動。`status` 就是為這件事存在的,它拿行事曆與提醒事項的現況校正草案,分成五類回報。

| 類別 | 意思 | 該做什麼 |
|---|---|---|
| 動過 | 事件被拖到別的時間 | 草案已自動校正,不用問 |
| 刪掉 | 事件被刪但待辦還在 | 問是取消還是要重排 |
| 提早 | 排在後面卻已勾完成 | 問要不要把後面的往前拉 |
| 逾期 | 到期了還沒勾完成 | 問是順延還是砍掉 |
| 今天 | 今天原訂幾件 | 唸給他聽 |

**早上的互動順序是固定的:先報現況,問他怎麼處理,得到回答後才重排。** 不要一早自動把行程改掉,那樣他看到的會是一份沒同意過的計畫。

```bash
python3 workplan.py shift              # 預覽,只動逾期未完成的
python3 workplan.py shift --apply      # 套用
python3 workplan.py shift --reflow --apply # 後續一起重排
```

`shift` 預設**只動逾期未完成的那幾件**,已排好又還沒到期的一律不碰,逾期項只會去找還空著的縫隙塞進去,不會把後面的推開。這是刻意的:每次調整都整批重排的話,行事曆上的安排每天長得不一樣,使用者會失去對計畫的信任。

縫隙不夠時腳本會直接列出「這幾件找不到空檔」,那時要問使用者是延長週數還是砍範圍,不要自己決定,更不要為了塞進去而動他已經確認的安排。

`--reflow` 才會把後續未完成的項目一起重排:逾期項排最前,其餘照原順序遞補。這同時涵蓋兩個方向,提早做完時後面往前拉,落後時後面往後順延。舊名 `--pull` 仍然可用。

`rebalance` 是舊的順延指令,只改待辦日期不動行事曆事件,`shift` 是它的超集。新的調整一律用 `shift`。

## 跟使用者互動時的原則

規劃結果一律先呈現再寫入,不要跳過確認直接 commit。清單歸屬每次都問,不要記成固定規則。挑選重點任務時給建議但由使用者決定,可以指出哪幾件到期日最近或難度最大值得卡時間。容量不足或順延過多時把選擇權交回去,提供延長週數與砍範圍兩個方向讓使用者選。

**估時一律從 30 分鐘起跳,不要一開始就抓很久。** 不確定的時候給 30 分或 60 分,不要動不動就估三小時。抓太久會把一天的空檔吃光,而且行事曆看起來壓力很大。真的做不完再追加時段,那比一開始就佔掉半天好。

**空檔不足時,壓縮的是既有行程,不是新任務的時長。** 使用者的意思是既有事件可以縮短來騰出空間,不是把新任務砍短。無論哪一種調整都要先問過,列出具體時段讓使用者選,不要自己決定。

**重排永遠是最後手段,而且要先問。** 他拖動了某個事件不代表整份計畫要重算,`status` 校正完就好。只有他明講要調整、或有項目逾期時才動 `shift`,而且先給預覽再套用。

報告呈現時直接把腳本輸出貼給使用者看即可,那是照八十字元終端機寬度排版的,不要再自己重排成表格。

## 技術注意事項

存取提醒事項與行事曆一律透過 `bin/wpkit`,那是用 EventKit 寫的 Swift 工具。不要改回 AppleScript 或 JXA,因為 AppleScript 讀行事曆要三分半,EventKit 只要幾十毫秒,實測 `today` 從 212 秒降到 0.7 秒。

`src/Info.plist` 的兩個 usage description key 必須嵌入執行檔,否則 EventKit 會被 TCC 直接拒絕而且連彈窗都不出現。編譯一定要走 `src/build.sh`,它會處理 `-sectcreate` 嵌入與 ad-hoc 簽章。改過 `wpkit.swift` 之後要重跑一次。

行事曆權限分成僅新增事件與完整存取兩級,只有完整存取才能讀取事件。如果讀取失敗,到系統設定的隱私權與安全性點行事曆,確認終端機那一項是完整存取。

待辦只有日期沒有時間,靠 EventKit 的 `dueDateComponents` 只填年月日達成,不要改成填入 hour 與 minute。

## 原生標籤是怎麼做到的

EventKit 沒有標籤 API,ReminderKit 私有框架的寫入會被權限擋,把 `#標籤` 寫進標題也只是純文字。唯一可行的路徑是捷徑:`is.workflow.actions.setters.reminders` 這個動作配上 `WFContentItemPropertyName = Tags`,才能設定真正的標籤。

流程是 EventKit 先建立提醒,接著呼叫捷徑用標題與清單名稱把那筆找出來補標籤。捷徑只能靠標題定位,而不同專案的任務名稱常常一樣,例如兩個專案都有「分析新需求」,所以 `create_tagged()` 建立時先用帶專案與序號的唯一標題,掛完標籤再改回正式標題。這三步不能省,少了中間那層兩筆同名的待辦會標到同一筆。

標籤名稱不分大小寫,`ABC` 會併進既有的 `abc`。要讓側邊欄顯示成大寫得在提醒事項 app 裡重新命名標籤,程式做不到。

捷徑檔在 `shortcuts/workplan-tags2.shortcut`,是從上游 `AdvancedReminderEdit` 刪掉 url、子任務、輸出等動作後重簽的精簡版,只留標籤邏輯。原版執行完會回傳退出碼 1 並顯示 Running was cancelled,精簡版是乾淨的 0。

要重建或修改捷徑,注意兩件事。第一,`shortcuts sign` 的輸入檔**副檔名必須是 `.shortcut`**,叫 `.plist` 或其他名字都會回報格式錯誤,這個錯誤訊息完全沒有提示這點。第二,不要用 Python 的 `plistlib` 讀寫捷徑檔,它會遺失資料(實測 6348 bytes 變 5322)導致簽署失敗,要改用系統的 `plutil -replace` 與 `plutil -remove` 原地修改。

驗證標籤有沒有真的掛上,不要看 `ZREMCDHASHTAGLABEL` 那張表,那只是最近使用過的標籤快取,跟提醒沒有關聯。真正的關聯在 `ZREMCDOBJECT` 表裡 `Z_ENT=32` 的記錄,`ZNAME1` 是標籤名稱,`ZREMINDER` 系列欄位是提醒的外鍵。資料庫路徑是 `~/Library/Group Containers/group.com.apple.reminders/Container_v1/Stores/Data-*.sqlite`,要連 `-wal` 與 `-shm` 一起複製出來才讀得到最新狀態。

`references/project_map.json` 分成 `prefixes` 與 `aliases` 兩塊。新增專案 database 時在 `prefixes` 補一行,沒補的話會自動用 database 名稱去掉「任務追蹤-」當前綴。使用者提到新的口語說法時在 `aliases` 補一行,對應到既有前綴即可。

路線圖快取用 `workplan.py roadmap --refresh` 更新,年度計畫頁的季度表格改動後要跑一次。

`plan` 大約要八秒,全部花在 Notion 的十二個 database 查詢,其餘子命令都在一秒內。
